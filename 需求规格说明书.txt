1. 项目概述
================================================================================

1.1 项目背景

    随着长租公寓市场的快速发展，公寓运营管理面临房源信息维护效率低、租约流程
    繁琐、账单管理混乱、租客服务体验差等痛点。易选好寓平台旨在构建一套覆盖房源
    管理、租约签约、账单支付、报修服务、智能咨询等全链路的一站式公寓运营管理
    平台，帮助公寓运营方提升管理效率，为租客提供便捷的租住体验。

1.2 项目目标

    - 提供完整的公寓房源信息管理能力（公寓、房间、配套、标签、属性等）
    - 实现从预约看房 → 签约 → 支付 → 退租的全流程线上化
    - 支持支付宝、微信、混合支付等多种支付方式
    - 提供报修工单管理系统
    - 集成AI智能对话助手，为租客提供智能咨询服务
    - 构建租户画像体系，辅助运营决策

1.3 系统范围

    系统包含两套独立的Web后端服务：
    - 管理端（web-admin）：面向公寓管理员，端口 8081
    - 租客端（web-app）：面向租客用户，端口 8082

================================================================================
2. 系统角色与用户画像
================================================================================

2.1 系统管理员（Admin）

    - 拥有后台管理系统的完整操作权限
    - 负责公寓与房源信息的维护、租约审核、账单管理、报修处理等
    - 通过用户名+密码+图形验证码登录

2.2 普通管理员（Common System User）

    - 拥有后台管理系统的部分操作权限
    - 由系统管理员创建并分配岗位
    - 负责特定业务模块的日常运营

2.3 租客用户（Tenant）

    - 使用租客端应用浏览房源、预约看房、签约租赁、支付账单
    - 通过手机号+短信验证码登录
    - 可查看个人租约、账单、报修进度等信息

2.4 AI助手（系统角色）

    - 基于DeepSeek大模型，为租客提供7×24小时智能对话咨询
    - 支持查询公寓信息、房间信息、设施配套等
    - 具备会话记忆和位置感知能力

3.1 管理端功能需求
--------------------------------------------------------------------------------

3.1.1 登录认证模块

    需求编号：A-001
    功能描述：管理员通过用户名、密码和图形验证码登录后台管理系统
    详细需求：
    - F-A-001-1：系统生成图形验证码（EasyCaptcha），存储至Redis，有效期60秒
    - F-A-001-2：管理员输入用户名、密码和验证码进行登录
    - F-A-001-3：登录成功后返回JWT Token，有效期10小时
    - F-A-001-4：后续请求需在Header中携带 Authorization: Bearer <token>
    - F-A-001-5：支持获取当前登录用户个人信息

3.1.2 公寓信息管理模块

    需求编号：A-010
    功能描述：管理员对公寓信息进行完整的增删改查操作
    详细需求：
    - F-A-010-1：新增公寓时需填写名称、简介、地址（省/市/区+详细地址）、经纬度、
                  联系电话，并关联配套设施、标签、杂费
    - F-A-010-2：修改公寓信息时支持同步更新关联的配套、标签、杂费
    - F-A-010-3：分页查询公寓列表，支持按区域、发布状态等条件筛选
    - F-A-010-4：查看公寓详情时返回配套列表、标签列表、图片列表、杂费列表
    - F-A-010-5：删除公寓前需校验是否存在关联房间，存在则禁止删除
    - F-A-010-6：支持发布/取消发布公寓

3.1.3 房间信息管理模块

    需求编号：A-020
    功能描述：管理员对房间信息进行完整的增删改查操作
    详细需求：
    - F-A-020-1：新增房间时需填写房间号、月租金、所属公寓，并关联属性值（朝向、
                  面积等）、配套设施、标签、图片、可选租期、可选支付方式
    - F-A-020-2：修改房间时支持同步更新所有关联信息
    - F-A-020-3：分页查询房间列表，支持按公寓、发布状态等条件筛选
    - F-A-020-4：查看房间详情时返回属性、配套、标签、图片、租期、支付方式
    - F-A-020-5：删除房间前需校验是否存在有效租约，存在则禁止删除
    - F-A-020-6：支持发布/取消发布房间
    - F-A-020-7：支持根据公寓ID查询该公寓下的房间列表

3.1.4 基础配置管理模块

    需求编号：A-030
    功能描述：管理员维护系统运行所需的基础配置数据
    详细需求：

    （1）属性管理
    - F-A-030-1：管理属性名称（如朝向、面积、楼层等）的增删改查
    - F-A-030-2：管理属性值的增删改查，属性值需关联属性名称
    - F-A-030-3：删除属性名称时级联删除其下所有属性值

    （2）配套管理
    - F-A-030-4：管理配套设施的增删改查（如WiFi、空调、洗衣机等）
    - F-A-030-5：配套区分类型：公寓配套和房间配套
    - F-A-030-6：配套包含图标信息

    （3）杂费管理
    - F-A-030-7：管理杂费名称（如水电费、物业费等）的增删改查
    - F-A-030-8：管理杂费值的增删改查，包含单位名称
    - F-A-030-9：删除杂费名称时级联删除其下所有杂费值

    （4）标签管理
    - F-A-030-10：管理标签的增删改查（如近地铁、精装修等）
    - F-A-030-11：标签区分类型：公寓标签和房间标签

    （5）租期管理
    - F-A-030-12：管理可选租期的增删改查（以月数为单位）

    （6）支付方式管理
    - F-A-030-13：管理支付方式的增删改查（如押一付一、押一付三等）

4. 非功能需求
================================================================================

4.1 性能需求

    - NFR-001：数据库连接池最大连接数12，最小空闲连接10
    - NFR-002：数据库连接超时时间60秒
    - NFR-003：AI对话读取超时120秒，连接超时30秒

4.2 安全需求

    - NFR-010：所有业务接口需JWT Token鉴权
    - NFR-011：管理端密码使用MD5加密存储
    - NFR-012：验证码存储于Redis，图形验证码60秒过期，短信验证码10分钟过期
    - NFR-013：JWT Token有效期10小时
    - NFR-014：敏感信息（API Key、数据库密码等）应通过环境变量或配置中心注入

4.3 可用性需求

    - NFR-020：系统应提供Knife4j接口文档，便于前后端联调
    - NFR-021：全局统一返回格式 Result<T>（code + message + data）
    - NFR-022：全局异常处理，业务异常和系统异常分类响应

4.4 兼容性需求

    - NFR-030：后端基于JDK 17，Spring Boot 3.3.8
    - NFR-031：数据库使用MySQL 8.x
    - NFR-032：缓存使用Redis 6.x
    - NFR-033：对象存储使用MinIO 8.x（S3兼容协议）

5. 业务流程需求
================================================================================

5.1 租约全生命周期流程

    步骤1：管理员创建租约 → 状态为"签约待确认"
    步骤2：租客确认租约 → 状态变为"已签约"
    步骤3：系统自动生成租金账单（押金 + 周期性租金）
    步骤4：租客按账单进行支付
    步骤5（正常到期）：租期结束 → 状态变为"已到期"
    步骤5（提前退租）：租客申请退租 → 状态变为"退租待确认"
                        → 管理员确认退租 → 状态变为"已退租" → 触发退款
    步骤5（续约）：租客申请续约 → 状态变为"续约待确认"
                   → 管理员确认 → 创建新租约

5.2 支付流程

    步骤1：租客选择账单，进入支付预览页
    步骤2：选择支付方式（纯支付宝 / 纯微信 / 混合支付）
    步骤3：系统创建支付订单和支付明细
    步骤4：调用支付渠道完成支付
    步骤5：支付回调确认，更新订单状态为"已支付"
    步骤6：同步更新账单状态和租约支付状态
    步骤7（退款）：申请退款 → 原路退回至支付宝和/或微信

5.3 报修流程

    步骤1：租客提交报修工单 → 状态为"待处理"
    步骤2：管理员查看并指派处理人 → 状态变为"处理中"
    步骤3：处理人添加进度记录
    步骤4：处理完成 → 状态变为"已完成"
    或：租客撤销报修（仅"待处理"状态可撤销）→ 状态变为"已取消"

5.4 预约看房流程

    步骤1：租客创建看房预约 → 状态为"待看房"
    步骤2：看房完成 → 管理员更新状态为"已看房"
    或：租客取消预约 → 状态变为"已取消"

6. 数据需求
================================================================================

6.1 数据库设计概要

    数据库名称：lease
    字符集：UTF-8
    共约39张表，分为以下类别：

    （1）基础数据表（11张）
        province_info、city_info、district_info、facility_info、label_info、
        attr_key、attr_value、fee_key、fee_value、lease_term、payment_type

    （2）房源核心表（3张）
        apartment_info、room_info、graph_info

    （3）关系关联表（8张）
        apartment_facility、apartment_fee_value、apartment_label、
        room_attr_value、room_facility、room_label、room_lease_term、
        room_payment_type

    （4）用户体系表（4张）
        user_info、system_user、system_post、user_balance

    （5）交易核心表（6张）
        lease_agreement、rent_bill、payment_order、payment_detail、
        refund_record、balance_transaction

    （6）交互行为表（6张）
        view_appointment、browsing_history、room_collect、repair_request、
        repair_progress、repair_attachment

    （7）数据分析表（1张）
        tenant_profile_features

6.2 公共字段约定

    所有表均包含以下公共字段：
    - id：主键，自增
    - create_time：创建时间，自动填充
    - update_time：更新时间，自动填充
    - is_deleted：逻辑删除标志（0未删除，1已删除）

6.3 枚举值定义

    预约状态：待看房(1)、已取消(2)、已看房(3)
    租约状态：签约待确认(1)、已签约(2)、已取消(3)、已到期(4)、
              退租待确认(5)、已退租(6)、续约待确认(7)
    账单状态：待支付(0)、已支付(1)、已逾期(2)、已取消(3)
    支付状态：待支付(0)、已支付(1)、已关闭(2)、已退款(3)
    报修状态：待处理(1)、处理中(2)、已完成(3)、已取消(4)
    报修优先级：低(1)、中(2)、高(3)
    支付方式：支付宝(1)、微信(2)
    支付组合：未选择(0)、纯支付宝(1)、纯微信(2)、混合支付(3)
    退款状态：处理中(0)、退款成功(1)、退款失败(2)
    余额交易类型：充值(1)、消费(2)、退款(3)、冻结(4)、解冻(5)
    发布状态：已发布(1)、未发布(0)
    用户状态：正常(1)、禁用(0)

7. 接口需求
================================================================================

7.1 接口规范

    - 所有接口返回统一的 Result<T> 格式：{ code, message, data }
    - 成功状态码：200
    - 接口文档：Knife4j / OpenAPI 3，访问地址 http://localhost:<port>/doc.html
    - 认证方式：JWT Bearer Token，Header名称 Authorization

7.2 状态码定义

    200 — 成功
    201 — 失败
    301 — 管理员用户名不存在
    302 — 管理员密码错误
    303 — 管理员验证码错误
    304 — 管理员账号被禁用
    305-312 — 管理端其他业务错误
    501 — 租客验证码错误
    502 — 租客手机号不存在
    503-507 — 租客端其他业务错误
    601 — 令牌无效
    602 — 令牌过期

7.3 外部接口依赖

    - 阿里云短信服务（dysmsapi.aliyuncs.com）：发送短信验证码
    - DeepSeek API（api.deepseek.com）：AI对话能力
    - MinIO（S3兼容协议）：文件对象存储
